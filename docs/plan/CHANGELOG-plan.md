# Plan changelog

Record here every place where implementation reality differed from the plan
documents, and every locked decision that had to change, with the reason.
Newest first.

| Date | Task | What differed | What was done |
|---|---|---|---|
| 2026-09-17 | M2-T08 | Nothing in the plan says where `eavery-cli` gets its data directory, and `03-architecture.md` §8 names one fixed location | A global `--data-dir`, then `$EAVERY_DATA_DIR`, then `ProjectDirs::from("dev", "eavery", "Eavery")`. The tests need a data directory that is not the user's, and so does anyone trying the CLI on a copy of a real folder before trusting it with the original. |
| 2026-09-17 | M2-T07 | `03-architecture.md` §6 has restore as a method on the turn engine, which holds an engine | Undo also exists as `turn::restore_without_session`, taking a store and a Journal and no engine at all. `eavery-cli undo` has no conversation open and must not have to start one — Undo is the button that makes everything else safe to try. The one thing the engine-less path does not do is write a `Restored` event, because `events.session_id` is not nullable and there is no session to attach it to. If M3 needs a restore made outside a conversation to appear in a transcript, that column becomes nullable in migration 0002. |
| 2026-09-17 | M2-T07 | C13 says one turn per Project and a restore refused while a turn runs | Held in the turn engine, which is per process. Two `eavery-cli` invocations against the same Project at the same time are not stopped by anything: there is no cross-process lock. That is the CLI's problem rather than the product's — the desktop app is one process — but it is worth knowing before scripting the CLI in a loop. |
| 2026-09-17 | M2-T07 | `06-plan-gate-permissions.md` §3.1 classifies a tool call from its `kind` and `locations`; `PermissionView` carries neither | `PermissionView` gained `kind` and `locations`, and the turn engine reclassifies every permission request before the user is shown it. Without this an edit outside the Project — which Undo cannot reach, and which §3.1 calls `Destructive` — would have been auto-allowed in direct mode as `Reversible`, on the strength of a guess made by the layer that does not know where the Project is. The M4-T02 `policy::classify` replaces the private function that does it now, adding the Connector registry it needs for the `outbound` flag. |
| 2026-09-17 | M2-T06 | `03-architecture.md` §8 gives the schema as seven bare `CREATE TABLE`s with no types enforced, no foreign keys, and the audit table's append-only rule stated as "no UPDATE or DELETE statements exist in the code for it" | The schema carries the rules instead. Every table is `STRICT`, so a column typed `TEXT` refuses an integer rather than handing one back later to a `parse` that cannot fail gracefully. `sessions`, `turns`, `events` and `checkpoints` have foreign keys onto their parents with `ON DELETE CASCADE`, and the store sets `PRAGMA foreign_keys = ON` on every connection — SQLite defaults it off, which would make the cascades decoration. `audit` has no foreign key at all, because a cascade from `projects` would be a DELETE: removing a Project forgets its conversation and keeps its decisions. The append-only rule is two triggers that `RAISE(ABORT)`, tested from a second connection that knows nothing about this crate; a rule that lives only in the callers holds until someone writes a new caller. Timestamps are RFC 3339 in UTC with nine fractional digits, fixed width, so `ORDER BY` on the column is chronological. |
| 2026-09-17 | M2-T06 | Nothing in the plan says how an event finds its `turn_id` on the way into the `events` table | `CoreEvent::turn_id()` was added and `append_event(session_id, event)` reads it off the event rather than taking it alongside: a caller that got the two out of step would write a transcript that cannot be reassembled. Two variants answer `None` — a restore happens between turns, and an engine's status is not about one — and a `CheckpointCreated` takes the turn from the checkpoint it carries, so the event and the checkpoint cannot disagree. |
| 2026-09-16 | M2-T05 | C12 says to pack loose objects above 5,000 with `git2`'s `Odb` / `packbuilder` | Not done, and deliberately left out rather than half-written. Writing a pack is the easy half; the space is only reclaimed by deleting the loose copies once the pack holds them, libgit2 exposes no `gc`, and hand-rolling object deletion against a user's only copy of their documents is not something to invent in passing. `Journal::loose_object_count()` reports the number so Settings can show it and so the design decision is taken with a figure in front of it. Everything else in M2-T05 — `unprotected()`, `size_on_disk()`, the guards, `scan_project` — is done. |
| 2026-09-16 | M2-T03 | `05-git-journal.md` §3 says to decide which deltas get a text diff with `blob.is_binary()` | `git2::Patch::from_diff` does not answer `None` for a binary delta; it produces a patch whose body is "Binary files a/x and b/x differ" and which has no hunks. The rule is therefore "no hunks, no text diff", which also covers a mode-only change and a delta whose patch is not UTF-8. A test on real `.xlsx`-shaped bytes holds it down. |
| 2026-09-16 | M2-T01 | `05-git-journal.md` §3 creates the Journal with `RepositoryInitOptions::workdir_path(root)` | That writes a gitlink file into the Project folder, which §1 forbids outright — a user's `git status` in their own documents folder would answer for Eavery's history — and libgit2 refuses it altogether when the Project is already a git repository ("cannot overwrite gitlink file"), which would leave everyone who works in git unable to have their folders protected. The repository is initialised bare and given its work tree through `core.worktree` instead, with no gitlink. A Project that is already a repository keeps its own `.git`, and a test asserts both that and that Eavery's history excludes it. |
| 2026-09-16 | M1-T05 (partial) | `04-acp-engines.md` §9 step 3 detects "needs sign-in" from a non-empty `authMethods` plus an auth error on `session/new`. The Claude adapter does neither half. | Adapter 0.78.0 reports `authMethods: []` whether or not the user is signed in, and an unauthenticated `session/new` fails with a bare `-32603 Internal error`. The sign-in state arrives instead as an unprompted notification on a vendor-extension method, `_auth/status_update`, with `{"authStatus":{"kind":"none","label":"Not logged in"}}`. Nothing was built on it: a rule derived from the not-signed-in case alone cannot be checked against the signed-in one, and `eavery-acp` is meant to hold no engine-specific knowledge. Health checks report the engine as `Unavailable` with the session error as the developer-facing reason until M1-T05 decides. Full record, including the initialize response (protocol v1, `loadSession: true`, `promptCapabilities.embeddedContext`, `mcpCapabilities` http+sse), in `manual-tests/M1-claude-partial.md`. |
| 2026-09-16 | M1-T03 | `04-acp-engines.md` §9 does not say what happens when an adapter is installed but the CLI it drives is not | Reported as `NeedsSignIn` without spending fifteen seconds on a handshake. `08-onboarding-packaging.md` §2 already says to check for the underlying CLI "because the adapter is useless without a login"; if there is no CLI there is no login, and the handshake can only arrive at the same answer more slowly. `EngineSpec` gained `sign_in_command` for the one command that screen shows verbatim (`07-ui-vocabulary.md` §5), which is not derivable from the other fields: Codex's is `codex login`, Claude's is `claude`. |
| 2026-09-16 | M1-T02 | The plan says to run the login-shell probe and "set it on the Eavery process" | The probed PATH is returned as data and threaded through discovery and into each engine child's environment instead. `std::env::set_var` is `unsafe` in edition 2024 — another thread reading the environment concurrently is undefined behaviour — and every crate here denies unsafe code. Passing the PATH to children is what mutating the process environment was for. `fix-path-env` itself was not used: it is the same probe without a timeout Eavery controls, and §C5 offers the equivalent. |
| 2026-09-16 | M1-T01 | `02-challenges.md` C5 says to use the `which` crate for discovery | Discovery resolves against a `Platform` parameter instead, with its own directory scan. `which` resolves for the host, so the Windows rules — `.exe` before `.cmd`, a `.cmd` shim launched through `cmd /C` — could only ever be tested on Windows, and path bugs that appear on one OS alone are exactly what M0 already lost a CI run to. The scan is about forty lines and every rule is now tested on all three platforms from any of them. |
| 2026-09-15 | M0 (CI) | The Windows verbatim-path hazard `06-plan-gate-permissions.md` §3.1 warns about is not confined to `policy::is_inside`; it bit the ACP layer and the CLI first | `std::fs::canonicalize` returns `\\?\C:\...` on Windows. That path was being used as the session `cwd`, so it went over the wire to the engine, which joined `{{cwd}}/notes.txt` onto it — and in a verbatim path a forward slash is not a separator, so the write landed nowhere. Two CLI tests failed on Windows and passed on Linux and macOS. Added `eavery-core::paths` (`canonicalize`, `canonical_or_self`, `nearest_existing`, `is_inside`) over the `dunce` crate, and routed the ACP layer and the CLI through it. The session cwd is normalised once, in `open_session`, because that is the path the engine is handed and joins onto for the rest of the session. M4-T02's `policy::is_inside` should call `paths::is_inside` rather than reimplement it. |
| 2026-09-02 | M0-T06 | The `agent-client-protocol` 2.x SDK is not usable here, so the documented §7 fallback was taken. D3 names that fallback, so this is not a change to a locked decision. | Four reasons, any one of them sufficient: (1) the SDK pins `agent-client-protocol-schema` at `=1.5.0`, so the workspace cannot also depend on the `1` line the plan asks for — cargo refuses to resolve; (2) it is built on `async-io` / `async-process` / `blocking` (smol) with no tokio, and the plan puts the rest of the workspace on tokio; (3) `AcpAgentConfig` has command, args and env but no working directory, which `04 §4` requires; (4) its stderr capture is internal and delivered only on exit, so nothing can read the ring while the engine is alive, which M1-T08 needs. Both crates stay in the workspace manifest for a later revisit, with the schema crate pinned to `=1.5.0` so the two can co-resolve if anyone adds them. |
| 2026-09-02 | M0-T06 | `PermissionView.request_id` is documented as "the JSON-RPC id as string" | It carries the tool call id instead. The JSON-RPC id is consumed by the dispatcher before the handler runs, and the tool call id is what the engine, the audit log and the UI all key on. Revisit if M4 needs to correlate two permission requests for one tool call. |
| 2026-09-02 | M0-T05 | The fake-agent script format in `11-testing-ci.md` §2 has no way to exercise the client's `fs/read_text_file` handler, and no way to script a mode change | Added two actions: `fs_read` (`{path, expectRefused}`) and `mode`. `fs_read` is what M4-T03 needs to test D15 — reads served from outside the Project — and `mode` lets a script prove the client reacts to `current_mode_update`. Also added an optional `protocolVersion` to the `initialize` section so a version-mismatch path can be tested. The script parser uses `deny_unknown_fields` throughout: a typo in an action name fails at load time rather than silently replaying a shorter script than the test author wrote. |
| 2026-09-02 | M0-T01 | Several crate versions in `03-architecture.md` §2 do not exist or are stale on crates.io | Pinned what crates.io serves: `git2` 0.21 (plan said 0.20), `rusqlite` 0.40 (0.32), `rmcp` 3.2 (0.8), `ts-rs` 12 (10), `which` 8 (7), `keyring` 4 (3), `calamine` 0.36 (0.26), `umya-spreadsheet` 3.1 (2), `rust_xlsxwriter` 0.99 (0.80), `pdf-extract` 0.12 (0.8), `lopdf` 0.44 (0.34), `quick-xml` 0.42 (0.37), `zip` 8 (2). `agent-client-protocol` 2.0.0 and `agent-client-protocol-schema` 1.7.0 are as planned. `fix-path-env` is not in the workspace manifest yet; it arrives with M1-T02. |
