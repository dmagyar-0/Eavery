# Review of the Eavery documents (September 2026)

Scope: every file in `README.md`, `docs/01..03-*.md`, and `docs/plan/*`. The
questions asked were: are there gaps or issues, is it feasible, does it make
sense, and is it worth building. Load-bearing technical claims were checked
against primary sources on 1 September 2026 (crates.io, npm, docs.rs,
agentclientprotocol.com, Anthropic's help centre, Zed's blog, the goose repo).

## 1. Verdict

**The engineering plan is unusually good. The product thesis has one crack
running through its centre, and the documents themselves supply the evidence
for it.**

- The architecture (ACP client, detached-git Journal, client-enforced plan
  gate, one event model with two vocabularies) is sound, cheap, and correctly
  borrows everything that is not differentiating. The plan documents are
  detailed enough that a competent implementer can start from them.
- Bet #1, "no API key, drive the AI you already pay for", is the headline
  differentiator and is also the weakest bet. It requires the office worker to
  already have a developer CLI installed and signed in. The user who has that
  is not the user the vision describes. For the user the vision does describe,
  the zero-key path is "open Terminal and run `npm install -g`", which is the
  API-key cliff wearing a different coat. See §3.1.
- goose itself now ships ACP providers (`claude-acp`, `codex-acp`) that use
  the user's Claude, ChatGPT, or Gemini subscription. Bet #1 is therefore
  already available in the open-source engine Eavery embeds, and goose's
  desktop app is moving to Tauri. Eavery's real differentiators are the
  Journal, the plan gate, and the Everyday vocabulary, not zero-key. The
  README and vision should say so.

**Recommendation:** worth building, but not yet as a 19-week commitment.
Spend two to three weeks on the three spikes in §7. If they pass, build the
plan as written with the fixes in §4 and §5. If the terminal-free zero-key
spike fails, the honest product is "BYO key or Ollama with excellent undo",
which is the same crowded position as Eigent and OpenWorker, and the Journal
should be shipped on its own instead (§7, option B).

## 3. Strategic issues

### 3.1 The target user does not have the prerequisite for the headline bet

Vision §1 defines the user as someone for whom managing API keys is
"disqualifying". Vision §4.1 and README bet #1 say Eavery solves this by
driving "the user's own, officially installed, officially authenticated Claude
Code or Codex CLI". `08-onboarding-packaging.md` §3 then tells that user to
install Node, run `npm install -g` twice, and sign in from Terminal.

An office worker with a Claude Pro or ChatGPT Plus subscription has the Claude
or ChatGPT app installed, not Claude Code or Codex CLI. So the zero-key path
serves developers and technical-adjacent staff, who are the same people the
docs admit will "evaluate" but not "use" the product. The onboarding claim in
the positioning table ("BYO-agent: no key") is true only for a population the
product is not aimed at.

This can be fixed, and fixing it is the single highest-value piece of work in
the plan:

- **Codex is fully downloadable.** Codex CLI publishes native binaries on
  GitHub releases and `@agentclientprotocol/codex-acp` ships platform
  binaries. Eavery can download both exactly as it downloads goose, then spawn
  `codex login` (a browser OAuth flow) from inside the app. That is a
  terminal-free zero-key path for anyone with a ChatGPT subscription, which is
  by far the largest consumer subscription base. None of this is in the task
  list; add it to M7.
- **Claude is not.** `claude-agent-acp` is a Node package built on the Agent
  SDK. Claude Code itself has a native installer, but the adapter needs Node.
  Options: bundle a Node runtime with the app, or accept that the Claude path
  requires Node and label it honestly. Decide this in the plan.
- **Gemini** is npm-only. Same as Claude.

Until this is done, the README should lead with the Journal and the plan gate,
not with zero-key.

### 3.2 The docs contradict themselves on whether the Claude zero-key path is "no grey zone"

`01-landscape.md` §4 states that from 19 February 2026, "Free/Pro/Max tokens
[are] not permitted in third-party tools or the Agent SDK". `04-acp-engines.md`
§3 states that the Claude adapter "uses the Claude Agent SDK". Vision §4.1
then claims the ACP route has "no grey zone". Those three sentences cannot all
be true.

The current facts (verified 1 September 2026): Anthropic's help centre says
Agent SDK and third-party app usage still draws from subscription limits and
nothing has changed; the May plan to bill it from a separate credit pool was
paused, not cancelled, and Anthropic has said a revised plan is coming. So the
Claude zero-key path is tolerated today and explicitly slated for change.
`02-challenges.md` C1 handles this correctly. The strategy documents do not.
Update `01-landscape.md` §4, `03-vision.md` §4.1, and the README so they say
what C1 says.

### 3.3 goose already does bet #1, and is heading for Tauri

goose's README now offers "your existing Claude, ChatGPT, or Gemini
subscriptions via ACP" through its `claude-acp` and `codex-acp` providers, and
discussion #7332 tracks its Electron to Tauri migration. That means the
embedded engine already contains the zero-key path, and goose's own desktop
app will shortly be an open-source Rust desktop agent with subscription
sign-in. Two consequences:

- Eavery's moat is not zero-key. It is the Journal, the plan gate, and
  Everyday mode, plus the office-document Connector and the Playbooks. The
  documents should rank the four bets accordingly.
- There is a real simplification available: use goose as the only engine, and
  let goose's ACP providers front Claude, Codex, and Gemini. Eavery would then
  need one launch matrix instead of five, and one set of mode and permission
  quirks to verify. The trade is that goose's provider wrapping adds a layer
  and its own quirks. Worth a one-day evaluation in M1 before committing to
  four direct integrations.

### 3.4 "Local-first" is only true on the Ollama path

Every file the engine reads goes to Anthropic, OpenAI, or Google on the
zero-key and BYO-key paths. The plan gate's "will leave this computer" section
covers Connectors, not the model. For the regulated-vertical story in vision
§5 and §6, only goose plus Ollama qualifies, and small local models are the
weakest at exactly the multi-file office tasks the wedge needs. Say this
plainly in the vision and in the plan card ("Your documents are sent to
{provider} to do this work").

### 3.5 No user contact before week 13

Vision §10 says to choose the wedge "from access to real users, not from
analysis" and to get five design partners "this month". The task list has no
user-facing task until M5-T07 (one usability tester, roughly week 13). Three
months of building before the first real finance or ops person touches it is
the biggest schedule risk in the plan and the cheapest to fix. See §7.

### 3.6 The wedge is the hardest document-fidelity case

The wedge is finance and ops reporting, whose artefacts are spreadsheets with
formulas, number formats, and charts, and decks. The v1 document Connector can
replace text in Word, append paragraphs, write cell values, and create a new
workbook. It cannot update a chart, preserve conditional formatting beyond
what `umya-spreadsheet` round-trips, or write `.pptx` at all. The first
bundled Playbook, `monthly-report-refresh`, will hit those limits immediately.
Either narrow the wedge for v1 (find-and-replace, reconciliation, summaries,
PDF table extraction are all fine) or move `.pptx` write and chart-aware
`.xlsx` editing forward.

## 4. Technical gaps and spec bugs

Concrete, in the order an implementer would hit them.

1. **Restore loses the user's uncommitted edits** (`05-git-journal.md` §3).
   `restore` diffs HEAD's tree against the target and writes only those
   deltas. Any file the user edited by hand since the last checkpoint is
   either left untouched (if not in the diff) or overwritten and lost (if it
   is). That violates D5. Fix: `restore` must first call
   `checkpoint("Before going back", Manual, force = false)` so HEAD equals the
   work tree, then diff. The test list in §7 should include "edit a file by
   hand, restore an older checkpoint, confirm the hand edit is recoverable".

2. **`Engine::cancel` cannot be called while `prompt` is running**
   (`03-architecture.md` §5). Both take `&mut self`, and `prompt` blocks until
   the turn ends, so the borrow checker forbids the one call `cancel` exists
   for. Make the trait `&self` with internal channels, or have `prompt` return
   a handle that owns `cancel`.

3. **The plan JSON never parses into `Plan`** (`03-architecture.md` §3 and
   `06-plan-gate-permissions.md` §2.3). The prompt asks for `steps` as an
   array of strings; `Plan.steps` is `Vec<PlanStep>`. `#[serde(default)]`
   does not rescue a type mismatch, so every well-formed plan falls back to
   raw markdown. Define a separate wire struct (`PlanJson`) and convert.

4. **The plan gate auto-allows the request that ends plan mode.** In Claude
   Code, leaving plan mode is itself a tool call (`ExitPlanMode`) that goes
   through the permission callback. Its ACP `kind` is most likely `other`,
   which `06` §2.2 allows during planning. Allowing it lets the engine start
   executing inside the plan prompt. M1-T05 must record how the adapter
   surfaces this call, and the plan-gate handler must reject it by title or
   raw input.

5. **Plan-mode detection misses Codex.** `06` §2.1 looks for a mode id
   containing `plan`. Codex exposes read-only, workspace-write, and
   full-access style modes, no `plan`. Its read-only mode is actually the
   strongest plan-phase enforcement available (OS sandbox, not a prompt).
   `EngineSpec` already has `plan_mode_hint`; make §2.1 use it and set it per
   engine.

6. **Refusing `fs/read_text_file` outside the Project breaks Playbooks.**
   `04` §1 refuses reads outside the Project; `09` §2.2 tells the engine to
   read `~/.eavery/playbooks/*/SKILL.md`. If the engine routes reads through
   the client (the Claude adapter does when the client advertises `fs`), the
   Playbook read fails. Reads are not dangerous; allow reads anywhere the
   engine could read itself, or at least the Playbook and bundle directories.

7. **Temp-file naming does not match the exclude rule.** `09` §1.1 writes
   `<path>.eavery-tmp` (a file suffix); `05` §3 excludes `.eavery-tmp/` (a
   directory). A crash between write and rename leaves `report.docx.eavery-tmp`
   tracked. Use one convention.

8. **Engines write their own state into the Project.** Claude Code creates
   `.claude/`, Codex may create `.codex/`, goose writes `.goose/` in some
   configurations. None are in the exclude list, so they get checkpointed and,
   worse, restored. Add them.

9. **No Journal retention or size policy.** "Nothing ever lost" plus forced
   pre-turn checkpoints plus 30 MB `.xlsx` blobs (already compressed, so git
   gains nothing) means the Journal grows without bound and libgit2 never
   packs or prunes. This is not a v1 blocker, but the docs need a stated
   answer: show Journal size in Settings, and decide whether an explicit,
   user-initiated "forget history older than N days" is allowed under D5.

10. **Cloud-synced folders are harder than C2 says.** OneDrive Files
    On-Demand, iCloud "Optimize Mac Storage", and Dropbox online-only files are
    placeholders; hashing them at the first checkpoint hydrates the whole
    folder from the cloud. The size guard is on bytes, not on placeholder
    status. Detect placeholder attributes (`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`
    on Windows, `.icloud` stubs on macOS) and treat them as "Not protected"
    until opened.

11. **First checkpoint on a 2 GB folder takes minutes with no UI.** `05` §4
    logs a warning above 10 s. Project creation needs a progress indicator and
    a cancel, or the first-run story ends on a frozen window.

12. **`is_inside` on Windows.** `canonicalize` returns `\\?\C:\...` paths;
    both sides must be normalised the same way or every path is "outside the
    Project" and every edit becomes Destructive. Known pitfall; note it in
    M4-T02.

13. **Health check at launch spends the user's subscription.** `02` C1 and
    `04` §9 send a real prompt to every detected engine at launch. Prefer
    `initialize` plus `session/new` for status, and run the prompt check only
    on demand or once per engine version.

14. **Durability summary uses streamed chunks.** `08` §7 builds the resume
    summary from "the last 20 `AgentText` events". `AgentText` is a streamed
    chunk, so that is roughly 20 tokens. Coalesce chunks into messages before
    counting.

15. **Vocabulary lint bans `json` and `token` in component source.**
    `07` §2 greps case-insensitively for words including `JSON` and `token`
    across component files. `JSON.stringify` and any auth-token variable will
    fail CI. Restrict the check to string literals and JSX text.

16. **Ctrl/Cmd+Z conflicts with text undo** in the composer (`07` §4 rule 5).
    Scope the shortcut to when the composer is not focused, or drop it.

17. **Tauri plugin naming.** `07` §1 lists the `shell` plugin for opening
    links and §3 uses `opener`. Tauri v2 moved link opening to `opener`; use it
    in both places.

18. **`mcpServers` for Codex and Gemini.** `04` §3 says that if an engine
    ignores `mcpServers`, Eavery writes the engine's global config after
    asking. That changes the user's terminal Codex too and is global, not per
    Project. Prefer the per-project config files where they exist and say so
    in the consent copy.

19. **No prompt-injection section.** An office folder is full of untrusted
    text (PDFs, emails, downloaded sheets). The design already mitigates this
    well (outbound always asks, edits are checkpointed, execute asks), but
    `02-challenges.md` should name the threat so the implementer does not
    weaken those rules for convenience. Two concrete rules: never auto-allow a
    Connector that can send, even if the plan listed it; and show the plan's
    `outbound` list in the digest even when empty.

20. **Concurrency is unspecified.** One turn per Project? Two Projects at
    once with two engine processes? Say which, because the Journal, the
    permission queue, and `core://event` sequencing all depend on it.

## 6. Schedule realism

The plan says 19 weeks for one implementer and calls the dates guidance. A
more honest range is 30 to 40 weeks for what is listed, because:

- M6-T05 (`docx_replace_text` across formatting runs, preserving every part)
  is a two-week task on its own once real documents with tracked changes,
  fields, and split runs show up. Budget it as such.
- M7 packaging (signing, notarisation, three installers, updater, clean-VM
  tests) is reliably underestimated; two to three weeks.
- M1 has four real-engine verifications, each of which will surface mode and
  permission quirks that feed back into M4. Expect M4 to be revisited.
- Cross-platform CI with vendored libgit2 and SQLite is fine, but Tauri
  builds on the Windows runner will cost days of yak-shaving the first time.

None of this changes the order, which is right: M0 → M1 → M2 first, UI later.

## 7. What to do before committing to the build

Three spikes, two to three weeks total, each with a pass/fail line:

1. **Terminal-free zero-key with ChatGPT.** Download Codex CLI and
   `@agentclientprotocol/codex-acp` binaries from inside a throwaway Tauri
   app, launch `codex login` from the app, drive one ACP prompt, and confirm
   the read-only mode blocks writes during a plan phase. Pass: a person with
   only a ChatGPT Plus account and no Terminal reaches a completed prompt.
   Fail: the product's onboarding claim has to be dropped.
2. **Journal on a real synced folder.** Detached git dir on a OneDrive or
   iCloud folder containing 500 MB of mixed Office files, with Excel holding
   one file open. Checkpoint, edit, restore, undo the user's own edit. Pass:
   byte-identical restore, locked file reported, no `.git` visible, no full
   re-hydration. Fail: C2 needs redesign before anything else is built.
3. **Docx find-and-replace preserving formatting** with `zip` + `quick-xml`
   on ten real documents from a finance or ops person (headers, footers,
   tables, fields, split runs). Pass: Word opens all ten without repair and
   the replaced text is correct. Fail: the wedge moves to tasks the Connector
   can do.

In parallel, and cheaper than any of the above: sit with three to five
finance or ops people and watch them do a month-end task with Claude Code or
Cowork on their own files. That tells you whether the engines can do the work
at all, which no document in this repo currently establishes.

**Option B if spike 1 fails.** Ship the Journal alone as a small open-source
tool ("a time machine for any folder an agent touches"): a CLI plus MCP
server that any Claude Code, Codex, goose, or Cowork user can point at a
folder today. It is the most portable idea in the repo, it is testable for
demand in weeks, and it builds the trust reputation the moat section says is
the asset. Everyday mode and the plan gate can be added on top later if
people want them.
